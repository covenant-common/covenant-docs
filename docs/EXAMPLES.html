Start with the agreement you actually need.

One report can begin with one exact offer. A company can add a scoped representative; continuing work can add budgets and milestones; a disputed delivery can use a separately agreed procedure. These examples show each result and the obligations it leaves open.

Try without installing: open the public browser demonstration. You control both synthetic roles, create real demonstration signatures and verify an exported record in another tab. It uses no AI model, real funds, account or blockchain transaction.

Public browsing and the standalone browser demo need no implementation access. Detailed source links below name an invited revision of the private implementation and require approved repository access. Some newer commands require that revision; the public task catalogue is an older snapshot.

Run the implementation: first obtain an owner-reviewed checkout or build and use its installed Python environment. Public package-registry installation is not offered here. Commands below are copied, never executed by this page. Keep actual private agreements and keys out of examples.

1. Buy one research report

Goal: “I run a small shop. I want a report, an exact price and a record of what we accepted.” Roles: buyer and supplier.

  1. Prepare one offer for 90 demo credits.
  2. Compare a counteroffer at 85; the changed price has a different fingerprint.
  3. Verify fresh buyer and supplier signatures. The old signatures must refuse the changed terms.

Run now: the first command drafts only; the second explicitly runs a fixed synthetic signing lesson with disposable in-memory keys.

python -m covenant_chain.quickstart
python -m covenant_chain.pilot demo

Expected result: DRAFT_REQUIRES_ASSENT at 90, then SYNTHETIC_AGREEMENT_VERIFIED at 85, with rejection of the old signatures. IDs differ between signing runs because keys are fresh.

What remains: report delivery, customer acceptance and separately authorised payment. A signature does not prove report quality, current business authority or a bank transfer.

Inspect the exact proposal and connect an agent
python -m covenant_chain.quickstart --full
python -m covenant_chain.quickstart --request > first-request.json
python -m covenant_chain.agent_server --keyless --stateless --once < first-request.json

The request file is an unsigned synthetic proposal. The stateless host performs no signing or payment. Pilot walkthrough · Owner-local application · Executable source.

2. Buy for a company without sharing its key

Goal: “My assistant can arrange a supplier report, but I need its authority and the supplier's promise to remain inspectable.” Roles: company principal, buying agent, supplier and guarantor.

  1. The company signs a grant limited to the exact agreement, role, context and time.
  2. The agent signs as Buyer while retaining the company's identity as principal. Supplier and Guarantor approve their own roles with their own keys.
  3. Merge partial approvals and assess authority under an independently adopted state snapshot and clock.
  4. Try changed terms and a revoked grant; both must refuse the relevant new verification while old signatures remain retained.
python -m covenant_chain.representation_owner demo

Expected result: ASSENT_VALID_UNDER_ADOPTED_AUTHORITY_STATE, three role approvals, Buyer mode DELEGATED, changed_terms_reject_old_signatures:true and revoked_grant_refuses_new_authority_check:true.

What remains: the recipient must adopt the state source, key/identity bindings and clock independently. The example does not establish company identity, legal effect, delivery, collateral or payment. Revocation does not automatically discharge an earlier obligation. No keys are saved and no funds move.

Use your own exact agreement

The fixed demo cannot sign an incoming document. Follow the represented-agreement owner guide to review an exact package, retain its fingerprint and sign through an existing restrictive owner key file. Agent tools prepare and inspect; they never receive a private key. Child-party assent is not inferred. Native GIVE grants are not automatically converted. Executable source.

3. Commission a series of reports

Goal: “I need recurring research, a total cap and an explicit choice before each job.” Roles: customer and provider, with separately signed master and calloff terms.

  1. Agree a 100.00 USD planning cap with no automatic dispatch.
  2. Approve a 25.50 USD calloff, retaining one expressly open final milestone.
  3. Record local allocation, reopen the journal and retry the identical request.
  4. Agree local cancellation; retry it without another release. The cap returns to 100.00 USD.
python -m examples.service_relationship_journey

Expected result: master_budget_minor:10000, allocated_minor:2550, both exact-retry flags true and remaining_after_local_cancellation:10000. The final milestone retains price:null, due_at:null and performance:UNASSESSED.

What remains: open terms need agreement; performance and actual payment need their adopted evidence. Releasing a local allocation is not an external refund. This example has payment_observed:false, refund_executed:false and execution_authorized:false.

Inspect how the agreements connect

Run from the reviewed repository root after installing its dependencies; source examples are not installed wheel commands. Each calloff has its own exact terms and signatures. A master signature cannot approve a missing calloff signature. The example uses synthetic integer time, not a trusted global clock. Continuing agreements · Executable source.

4. Deliver, disagree and recover after an interruption

Goal: “Pay for useful work once; if we disagree, use the procedure we actually chose.” Roles: buyer, supplier, primary decision-maker and appeal decision-maker.

First, complete a synthetic delivery: the example creates temporary owner-configured roles, runs proposal → acceptance → delivery → release → observation, and retries the original release request.

python -m examples.agent_native.shared_work_order

Expected result: PASS, seven separate-process calls, synthetic balances buyer 910 / supplier 90, and retry_debited_twice:false. The adopted local provider observes its own reference balance; a reader carrying only the signatures reports carried_payment_observed:false.

Exercise an actual partial award, appeal and lost-reply recovery

  tests.test_bilateral_v2_security.BilateralSecurityTests.test_lost_reply_recovers_original_signed_receipt_without_second_charge

Run in the contributor environment from the reviewed repository root. Expect three tests and OK. The first allocates 50 of 100 synthetic units to each side; the appeal case preserves the primary decision but gives effect to the final overturn; recovery returns the retained receipt without another debit. These tests exercise the actual protocol paths, not a real court or independent arbitrator.

What remains: all custody here is temporary synthetic local SQLite. No external USDC, x402 settlement, chain ledger or independent operator is qualified. Payment completion does not establish deliverable quality. Work-order profile and owner setup · Executable source.

5. Record one licensed content use

Goal: “I publish content and want a particular crawler use tied to exact purpose and payment evidence.” Roles: publisher, crawler and adopted payment observer.

  1. Adopt an exact synthetic offer for one resource and a declared RAG/private-research purpose.
  2. Observe payment as unknown before a separately invoked local demo transfer.
  3. Record the signed per-use receipt; retry it idempotently.
python -m examples.crawl_licensing_demo

Expected result: CRAWL_PAYMENT_UNKNOWN, then receipt RECORDED and retry IDEMPOTENT. What remains: external_payment:false, access_authorized:false and legal_rights_established:false. Recording a receipt does not prove title or unlock an outside website. Publisher guide · Executable source.
